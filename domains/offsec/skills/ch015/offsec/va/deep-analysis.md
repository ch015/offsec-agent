# Phase 2: 원칙 기반 심층 분석 (Principle-Based Deep Analysis)

Phase 1이 아키텍처 차원별 "구조적 이슈"를 찾는 반면, Phase 2는 **보안 원칙에 기반한 자유 추론**으로 Phase 1에서 다루지 않은 영역을 탐색합니다.

```yaml
Security_Principles:
  Least_Privilege: "모든 주체에 필요한 최소 권한만 부여"
  Defense_in_Depth: "단일 보안 레이어가 아닌 다층 방어 구조"
  CIA_Triad: "기밀성, 무결성, 가용성"
  Secure_Defaults: "기본 설정이 안전한 상태 (deny by default)"
  Trust_Boundary_Verification: "모든 신뢰 경계에서 데이터 검증"

Free_Exploration_Areas:
  Business_Logic:
    methodology: |
      프로젝트의 비즈니스 도메인을 이해하고 다음 가능성을 추론:
      가격/수량/자격 조작, 이중 지불(토큰, 쿠폰, 투표),
      상태 전이 우회(결제 전 서비스 사용), 비즈니스 규칙 우회(한도 초과)

  Cryptography:
    methodology: |
      암호화 관련 코드를 식별하고 목적 적합성을 판단:
      1. 식별: 해싱, 암호화, 서명, 난수 생성, 키 유도 관련 코드 검색
      2. 목적 분류: 각 사용의 보안 목적 이해
      3. 적합성 판단:
         - 알고리즘/도구가 목적에 적합한가?
         - 파라미터가 충분한가? (salt, IV/Nonce, 키 길이 등)
         - 구현이 안전한가? (IV 재사용, timing-safe 비교, 폐기된 API 등)
      4. 병렬 경로 교차 대조:
         동일한 목적의 암호화 작업이 여러 경로로 제공되는 경우
         (예: 서명 A, 서명 B, 서명 C) 각 경로의 보안 속성을 비교한다.
         한 경로에 적용된 보호(도메인 분리, 컨텍스트 바인딩, 파라미터 검증)가
         다른 경로에 누락되어 있는지 확인한다.
         보호 수준이 다른 경로는 우회 벡터가 될 수 있다.

  Timing_Races_and_Concurrency:
    기본_분석: |
      concurrency.md 미로드 시에도 아래 최소 질문은 수행:
      - "원자적이어야 하는 작업이 DB 트랜잭션/잠금 없이 수행되는가?"
      - "읽기→검증→쓰기 사이에 다른 요청이 개입 가능한가?"
    확장_모듈: |
      금융/큐/분산 서비스 감지 시 offsec/va/concurrency.md를 로드하여
      5개 분석 영역(TOCTOU, 분산 원자성, 멱등성, 캐시 일관성, 큐 순서)을 체계적으로 수행.

  Privacy:
    review: |
      - 불필요한 PII 수집이 있는가?
      - 데이터 보존 기간이 정의되어 있는가?

  AI_Integration:
    methodology: |
      AI/LLM 통합 코드를 식별하고 다음을 추론:
      1. 프롬프트 인젝션 체인: 사용자 입력 → (DB/벡터 스토어) → 프롬프트 → LLM → 출력 사용
         각 단계에서 검증/새니타이징이 있는가?
      2. 데이터 유출 체인: 민감 데이터 → 프롬프트 → 외부 LLM API → 로그
         각 단계에서 PII/시크릿 필터링이 있는가?
      3. 에이전시 남용: LLM 결정 → 도구 호출 → 시스템 상태 변경
         인간 검증 없이 위험한 작업이 실행될 수 있는가?
      4. RAG 포이즈닝: 외부/사용자 콘텐츠 → 벡터 스토어 → 검색 결과 → 프롬프트
         악의적 콘텐츠가 RAG 파이프라인을 통해 프롬프트에 주입될 수 있는가?
      5. 모델 DoS: 사용자가 의도적으로 긴 입력/복잡한 요청으로
         토큰 소비를 극대화할 수 있는가? 비용 제한이 있는가?

  Mobile_Platform:
    methodology: |
      모바일 플랫폼 고유 보안 위협을 추론:
      1. 루팅/탈옥 탐지: 기기 무결성 검증이 있는가?
         탐지 시 앱 동작이 적절히 제한되는가?
      2. 런타임 조작 방어: Frida, Xposed 등 후킹 프레임워크에 대한
         방어가 비즈니스 요구사항에 적합한가?
      3. WebView 보안: WebView를 사용하는 경우
         JavaScript 인터페이스가 최소 권한인가? 로드하는 URL이 제한되는가?
      4. 푸시 알림: 알림 페이로드에 민감 데이터가 포함되는가?
      5. 백그라운드 처리: 백그라운드에서 민감 작업 실행 시
         데이터 보호가 유지되는가?

  SDK_Misuse_Resistance:
    methodology: |
      SDK를 사용하는 개발자의 실수로 보안이 약화되는 경로를 추론:
      1. 잘못된 초기화 순서: 인증 전에 API 호출이 가능한가?
         초기화 미완료 상태에서 SDK가 동작하면 어떤 보안 검증이 우회되는가?
      2. 설정 오용: 개발자가 테스트용 설정(debugMode, disableSsl)을
         프로덕션에 그대로 배포하면 어떤 위험이 발생하는가?
      3. 콜백/이벤트 오용: SDK 콜백으로 전달받은 민감 데이터를
         개발자가 로그에 출력하거나 UI에 표시할 가능성
      4. 동시성 오용: 멀티스레드 환경에서 SDK의 스레드 안전성
         SDK가 스레드 안전하지 않은 경우 명확한 문서화가 있는가?
      5. Deprecated API: 보안상 폐기된 API가 여전히 호출 가능한가?
         호출 시 경고 또는 차단이 있는가?

  Multi_Tenancy:
    methodology: |
      멀티테넌트 아키텍처를 식별하고 격리를 검증:
      1. 테넌트 식별: tenant_id, org_id, workspace_id 등
         테넌트 컨텍스트를 결정하는 메커니즘 식별
      2. 격리 일관성:
         - 모든 DB 쿼리에 테넌트 필터가 일관되게 적용되는가?
         - 미들웨어/ORM 레벨에서 자동 적용인가, 각 쿼리에서 수동인가?
         - 수동 적용이면 누락된 쿼리가 있는가?
      3. 교차 오염 경로:
         - 캐시 키에 테넌트 컨텍스트가 포함되는가?
         - 파일 업로드 경로에 테넌트 분리가 있는가?
         - 큐/이벤트 메시지에 테넌트 컨텍스트가 전파되는가?
         - 백그라운드 잡에서 테넌트 컨텍스트가 유지되는가?
      4. 테넌트 간 열거:
         - 다른 테넌트의 존재/이름/설정을 열거할 수 있는가?

Directive: |
  "Phase 1은 아키텍처 최소 리뷰. 위 보안 원칙에 기반하여
   Phase 1에서 다루지 않은 보안 구현 이슈를 자유롭게 탐색.
   프로젝트의 비즈니스 도메인을 고려한 고유 위협도 추론.
   위 영역은 시작점일 뿐 — 분석을 이에 한정하지 않는다."
```
