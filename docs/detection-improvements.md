# 독립 취약점 집계와 탐지 품질 개선

기준: 2026-10-08. [실행과 옵션](../README.md), [앱 내장](embedding.md).

후속 실제 검증과 최신 중지 상태는 [내부 진단 품질 검증 인수인계](verification-handoff-20261008.md)에 정리했다. 아래의 새 유료 진단 미실행 표시는 이 문서의 최초 집계 개편 시점 기준이다.

이번 변경은 **독립 취약점 집계 경로 수정과 90% 목표에 대한 상세 검토**다. 아래에서 구현 완료와 후속 설계를 구분한다. 새 유료 진단이나 Juice Shop 공격 실행은 하지 않았다. 기존 두 실행의 원장·보고서도 소급 수정하지 않는다. 구현 테스트 통과는 실제 정탐률 90% 달성을 뜻하지 않는다.

## 1. 현재 결과와 목표의 분모

기존 대상은 Juice Shop v19.2.1, commit `8d112d69a4c927579bc5e9ce0b4f2b3894bb4382`다. 비교 근거는 로컬 `out/implementation-20261007/challenge-comparison-20261008/`의 `comparison.json`, `comparison.csv`, `comparison.html`, `finding-index.json`, `validation.json`에 보존돼 있다. 이 자료는 기존 결과와 공식 111개 챌린지를 사후 대조한 것이며 독립 취약점 전체 정답셋은 아니다.

| 지표 | 1차 | 2차 | 해석 |
|---|---:|---:|---|
| 전체 후보 기록 | 314 | 300 | 중복·기각·불확실 포함 |
| CONFIRMED 기록 | 234 | 233 | 독립 취약점 수가 아님 |
| 공식 챌린지 직접 대응 | 72/111 (64.86%) | 76/111 (68.47%) | 원인·정확한 비밀값·대상 식별, 실행 성공 아님 |
| 부분 대응 | 18 | 16 | 필요한 조건/체인/정확한 대상이 덜 확인됨 |
| 대응 없음 | 21 | 19 | 비교 기준을 충족하는 기록 없음 |
| 독립 취약점 Precision / Recall / F1 | 미산출 | 미산출 | 전체 원인 정답셋과 전체 예측의 독립 판정 필요 |

양쪽에서 직접 대응한 항목은 68개, 두 결과 합집합은 80개다. 합집합을 단일 실행의 성능으로 보고하면 안 된다. 정적 소스 원인으로 분류한 챌린지 76개만 보아도 직접 대응은 60개/63개다. 이 76개 역시 서로 다른 독립 취약점 76건이라는 뜻은 아니다. 같은 결함의 여러 과제와 여러 결함이 들어 있는 단일 과제가 있다.

**권장 합격 목표**는 고정한 독립 원인 정답셋에서 Precision ≥90%, Recall ≥90%, F1 ≥90%다. Precision만 높이면 어려운 취약점을 보고하지 않는 방식으로 개선된 것처럼 보일 수 있다. Accuracy `(TP+TN)/전체`는 보안 비결함 전체의 분모를 정의하지 못하므로 주 지표로 사용하지 않는다.

- Precision = 독립 정탐 원인 수 / (독립 정탐 원인 수 + 독립 오탐 원인 수).
- Recall = 정답셋에서 찾아낸 독립 원인 수 / 적용 가능한 정답 독립 원인 수.
- F1 = `2 × Precision × Recall / (Precision + Recall)`.
- 카탈로그 밖 실제 결함은 독립 검증 후 별도 novel-valid로 인정한다. 고정된 정답셋 Recall의 분모를 사후에 바꾸지는 않는다.
- 관찰은 양성 예측과 분리한다. 관찰로 잘못 내린 실제 결함은 정답셋에서 FN으로 남겨야 한다. inconclusive/누락/실패를 분모에서 조용히 빼지 않고 보류율·미검증 양성 수·증거 유효율·중복률을 함께 공개한다.
- 비교용 원인 정답 ID는 평가자가 사전에 정한다. 에이전트의 `causeId`를 정답 ID로 그대로 쓰지 않는다.

만약 목표가 **111개 챌린지 대응률 90%**라면 최소 100개가 필요하다. 2차 대비 +24개다. 16개 부분 대응을 전부 직접 대응으로 올려도 92/111=82.88%로, 미대응 19개 중 최소 8개를 더 해결해야 한다. 현재 합집합 80개를 기준으로 해도 +20개가 필요하다. 독립 원인 정답셋이 완성되기 전에는 이 수치를 취약점 Recall이라고 부르지 않는다.

## 2. 독립 취약점 집계 — 구현 완료

기준은 **같은 구성요소의 같은 보안 통제 실패이며 독립적으로 고칠 수 있는 수정 경계가 같은가**다. 파일·행·제목·CWE·인용문이 같다는 사실만으로 합치지 않는다. 하나의 함수 안에서도 인증 우회와 정보 노출의 수정 지점이 다르면 별개 원인이다. 하나의 전역 설정 수정으로 없어지는 결함을 여러 테스트와 여러 호출자가 보고했다면 같은 원인으로 묶을 수 있다. 단순히 동일 패턴의 코드를 복사했다는 이유만으로 서로 다른 수정 지점을 한 건으로 만들지는 않는다.

| 항목 | 변경 내용 | 구현 위치 |
|---|---|---|
| 원인 분류 | Reviewer가 `kind`, `causeId`, `component`, `rootCause`, `fixBoundary`, 정확한 `primaryEvidence`를 명시 | `src/runtime/vulnerability-inventory.ts` |
| 관찰 구분 | 테스트 설명·도구 오탐 설명·취약점이 아닌 사실은 `kind: observation`과 사유로 분리. INFO/HIGH 같은 심각도로 자동 분류하지 않음 | 같은 파일 |
| 잘못된 병합 유도 제거 | 같은 인용문을 공유하면 강제 병합하던 오류를 비차단 검토 힌트로 변경 | `src/runtime/v2-review-resolution.ts` |
| 중복/수정 구별 | 검토된 동일 원인 중복은 영향·전제·미해결·근거를 보존. 수정으로 대체된 과거 주장은 복원하지 않음 | inventory / `report-appendix.ts` |
| 정합성 검사 | 같은 ID의 다른 정의, 같은 정의의 다른 ID, 근거 밖 인용, 다른 원인으로의 중복 병합, 충돌하는 보정 판정 검출. unsupported/abstain/escalate 주장을 중복 근거로 승격하는 것도 차단 | inventory |
| 새 실행 필수화 | 전체 Write와 20개 이하 patch 모두 원인 분류 요구. 미작성 draft는 보존하고 최종 완료 때 검사 | `domains/offsec.ts`, `review-artifact-patch.ts`, `missions/assess-v2.ts`, `missions/review-loop.ts` |
| 복구 | 분류 누락을 보완하면 실제 진전으로 인식. 기존 검토·읽기 영수증을 보존해 이어서 수정 | `review-progress.ts` |
| 평가·보고 | 호스트가 봉인한 원인 집계를 평가자가 그대로 사용. 독립 수/채택 기록 수/관찰 수/독립 심각도를 분리 | `evaluation-projection.ts`, `v2-evaluation.ts`, `report-appendix.ts` |
| 벤치마크 입력 | 새 분류 산출물에서는 원인당 한 예측으로 정규화하고 관찰·폐기된 주장 제외 | `evals/offsec/adapters/current-v2.ts` |

`causeId`는 Reviewer의 의미 판단에 붙인 실행 내 식별자다. 원본 파일 해시나 첫 줄 번호로 만들지 않는다. 호스트는 정의 문자열의 공백·개행을 정규화해 비교하지만 서로 다른 문장으로 쓴 동일 원인을 자동으로 이해하지는 못한다. 이 변경은 **잘못된 구조와 강제 병합을 줄이는 장치**이며 모델의 의미적 중복 판정이 항상 옳다는 보장은 아니다. 실행 간 재현성은 평가자의 정답 원인 ID에 매칭해 측정해야 한다.

기존 분류 없는 자료의 `independentVulnerabilityCount`는 `null`이다. 이를 0이나 CONFIRMED 기록 수로 대체하지 않는다. 따라서 과거 234/233건에 대해 현재 새롭고 정확한 독립 취약점 수를 산출했다고 주장하지 않는다. 과거 결과의 확정 수를 얻으려면 보존된 근거를 이용해 원인별 재분류·검토를 해야 한다. 예전 벤치마크의 기록 단위 정규화도 원인 단위 성능과 섞지 않는다.

보안 통제·영향·수정 경계로 묶는 접근은 독립 수정 가능성을 판단 요소로 사용하는 [CVE의 공개된 기존 CNA 규칙 설명](https://www.cve.org/Resources/Media/Archives/OldWebsite/cve/cna/rules.html)을 참고한 것이다. CVE 할당 규칙 전체를 구현했다거나 CVE 발급 단위와 항상 일치한다는 주장은 아니다.

## 3. 과거 결과에서 확인한 문제

### 3.1 잘못된 집계와 과도한 병합

- 1차 JSONP 기록 `F-192666939642`, `F-879059625794`가 필드 선택 문제 `F-884663184230`에 병합됐다. 공유 인용문이 있어도 콜백/응답 경계와 필드 접근 통제는 따로 판단해야 한다.
- NoSQL 연산자·다중 변경 `F-307569137562`가 리뷰 소유권 문제 `F-153086861117`에 병합됐다. 소유권 검사와 입력 연산자 제한은 별도 수정 경계다.
- 챗봇 표현식 문제 `F-391173301495`, `F-836429276375`가 모델 XSS 정제 `F-829204814009`에 합쳐졌다. 대표 제목만 세면 다른 메커니즘이 가려진다.
- 시드 자격증명 `F-216453381918`가 정적 로더 실패 `F-357907791459`에 합쳐진 사례도 있다. 기존 리뷰 사유에는 호스트의 중복 근거 검사를 통과하기 위한 병합이라는 설명이 나타난다.
- 2차 `F-118272226056`는 교육용 fixture가 실서비스 취약점이 아니라는 설명, `F-236927785862`는 정규식 `exec`에 대한 Semgrep 오탐 설명인데 CONFIRMED/INFO 기록에 포함됐다. 취약점 분류와 심각도는 별도 필드여야 한다.

기존 비교에서는 병합 기록도 직접 읽고 유효한 근거만 대표에 연결했다. 앞으로는 원인별 독립 집계와 영향 보존으로 이 수작업 의존을 줄인다. 여기 나열한 사례만으로 전체 614개 후보의 독립 원인 수나 전체 오탐 수를 추정하지 않는다.

### 3.2 파일을 읽었어도 빠진 보안 조건

양쪽 실행은 813개 파일을 대상으로 했으나 다음 항목은 직접 대응하지 못했다: Empty User Registration, Repetitive Registration, Zero Stars, Five-Star Feedback 삭제 권한, Retrieve Blueprint. 입력 존재 여부, 확인 필드 일치, 수치 하한, HTTP 메서드별 권한, 정적 파일 공개 경로를 체계적으로 확인하지 못한 흔적이다.

현재 `planning/analysis-assessments.ts`는 파일/흐름의 analyzed/deferred, 사유, 인용을 검증한다. **각 API에서 모든 입력·권한 검토를 끝냈는지는 강제하지 않는다.** 파일 읽기 성공과 보안 검토 충실도를 같은 완료율로 표시해서는 안 된다.

### 3.3 실행 조건보다 앞선 결론

BeeFaucet 관련 기록(1차 `F-496886973669`, 2차 `F-272299933907`)은 반복 인출로 HoneyPot 가격을 모으는 결론에 주의가 필요하다. 보존 소스의 Solidity `^0.8.0`, `uint8` 잔액 200, `balance -= amount`, `unchecked` 부재는 1000 BEE 확보 주장에 필요한 조건과 맞지 않는다. 이는 해당 배포 전체가 안전하다는 결론이 아니라 **기존 보고의 특정 공격 경로가 입증되지 않았다는 반증**이다. Solidity 0.8.0의 기본 overflow/underflow 검사 동작은 [공식 릴리스 설명](https://www.soliditylang.org/blog/2020/12/16/solidity-v0.8.0-release-announcement/)과 일치한다. 별도 `^0.6.12` ETHWalletBank의 재진입 결함까지 같은 이유로 기각하면 안 된다.

JWT alg:none/HS-RS 혼동, 브라우저 SameSite, 챗봇 500 응답과 이후 질의의 영구 실패도 버전·환경·실제 도달성을 분리해 검증해야 한다. 두 실행에서 발견한 Alchemy 키는 Leaked API Key 챌린지의 정확한 키와 다르므로 제목 유사도로 정탐 처리할 수 없다.

### 3.4 도구 범위와 의미 분석의 차이

기존 두 실행의 AST 통계는 622개 파싱, 191개 미지원, 35개 경고, 파싱 실패 0이다. 데이터 흐름은 설정 한도 200개에 도달했고 taint 경로는 0개다. Semgrep은 813개 요청 중 694개를 처리(전체 682, 부분 12), 119개는 적용 규칙 없음, 도구 후보는 양쪽 모두 9개였다. 이는 전체 파일 전달 완료와 별도 지표다. taint 0개를 오염 흐름이 없다는 증거로 쓰면 안 된다.

## 4. 90%를 위한 후속 변경 설계

아래 P1/P2는 이번에 구현한 것으로 표시하지 않는다. `analyze.md`에는 경계값·권한 조합·실행 조건 점검 지시를 추가했지만, 강제 검토 행렬·런타임 검증기·새 정답셋은 아직 후속 작업이다.

| 우선순위 | 변경 | 주요 위치 | 검증할 결과 |
|---|---|---|---|
| P0 완료 | 독립 원인/관찰 분리, 강제 인용 병합 제거, 증거 보존·집계 봉인 | inventory, review, projection, reporter, adapter | 과대 집계·잘못된 병합·평가 숫자 변조 회귀 차단 |
| P1-1 | 라우트·입력·권한별 검토 항목을 Scanner 계획에 포함하고 Analyzer 결과로 추적 | scanner-contract, task-planner, analysis-assessments, analyze | 알려진 5개 누락 유형을 놓치면 미완료로 남음 |
| P1-2 | 모듈을 가로지르는 호출·데이터·가드·상태 전이 연결 | dependency graph, scanner flows, shared-knowledge, analysis-revision | 부분 결과를 실행 전제까지 갖춘 경로로 연결 |
| P1-3 | 독립 반증 및 버전 고정 실행 검증 | reviewer, review-loop, 별도 로컬 검증 어댑터 | Solidity/JWT/브라우저/지속 실패에 대한 잘못된 단정 감소 |
| P1-4 | 취약/수정본 쌍과 전체 원인 라벨을 가진 평가셋 | offsec-benchmark, scoring, benchmark fixtures | 독립 Precision/Recall/F1과 FN을 실제로 계산 |
| P2-1 | 도구 규칙·언어 지원·잘린 흐름 보완 | AST context-builder, Semgrep rules, preanalysis-evidence | 규칙 추가의 고유 정탐 증가와 오탐 변화를 함께 측정 |
| P2-2 | 미해결 위험별 보완과 종료 사유 관리 | analysis-revision, review-loop, coverage | 작업 수 증가가 아니라 미해결 통제 감소를 진전으로 측정 |
| 별도 목표 | 외부 자료·이미지 메타데이터·퍼즐·체인 해결 | 별도 challenge 검증 도구/평가 트랙 | 111개 전체 목표를 원할 때 필요한 범위 보완 |

### P1-1: 보안 검토 항목을 실행의 일급 데이터로 만들기

Scanner가 파일 분할 외에 `surfaceId`, 진입점/메서드, 입력 구조, 인증 방식, 소유권/역할, 상태 변경, 민감 sink를 정리한다. 호스트는 발견한 라우트·모델·정적 파일 마운트와 비교해 계획 누락을 알려야 한다. Scanner가 놓친 라우트를 Analyzer가 추가 등록할 수 있어야 하며, 단순 import 그래프만으로 Express의 동적 등록을 완전히 추론했다고 가정하지 않는다.

각 항목은 `obligationId`, 대상, 적용 조건, `vulnerable / protected / unresolved / not-applicable`, 근거, 관련 finding/flow, 미해결 사유를 가진다. `protected`에는 실제 가드·검증기·DB 제약 증거, `not-applicable`에는 사유가 필요하다. 필수 항목의 답이 없으면 파일이 읽혔어도 semantic coverage 완료로 처리하지 않는다. 다만 이 행렬도 모든 미지의 결함을 증명하는 완전성 보장은 아니다.

최소 입력 조합은 누락/undefined/null/빈 문자열/공백/0/음수/최솟값·최댓값/경계 밖/타입 불일치/배열·객체/반복 필드다. 프런트 검증 존재와 서버 검증 존재를 구분하고 ORM setter·DB constraint까지 연결한다. 권한은 메서드 × 비로그인/일반/관리자 × 본인/타인 객체로 확인한다. 이 조합은 모든 프로젝트에 무조건 전수 곱하지 않고 해당 인터페이스의 적용 조건에 따라 생성한다.

완료 기준: 기존 5개 누락 유형과 각각 수정된 대조본에서, 취약본은 근거 있는 결함으로 보고하고 수정본은 같은 결함으로 보고하지 않아야 한다. 또한 소스 전달만 하고 검토 행렬을 비우는 테스트, 가드 이름만 쓰고 근거를 누락하는 테스트가 완료를 통과하지 않아야 한다.

### P1-2: 원인과 공격 경로를 분리하고 공통 근거를 재사용하기

유닛 경계를 지나면 경로를 `입력 → 변환/가드 → 저장/상태 → 민감 동작 → 영향`으로 연결한다. 예: 삭제된 상품 검색→주문, SQL UNION 합성 사용자→로그인 세션, soft-delete 계정→인증 조회, SVG 경로→redirect→외부 이미지, 프로필 username→챗봇 초기화→이후 질의 상태.

각 연결은 실제 심볼·라우트·변수·조건·버전과 증거를 가진다. Analyzer가 공통 관찰을 저장하고 연결 담당이 이를 참조하되, 다른 에이전트의 가설을 검증된 사실처럼 승격하지 않는다. `causeId`는 수정해야 할 결함, 별도 `chainId`는 여러 결함/조건으로 구성한 공격 경로를 뜻하게 설계한다. 하나의 원인에서 여러 영향이 나와도 취약점은 중복 세지 않고, 서로 다른 원인이 체인 하나를 구성해도 원인 수를 하나로 줄이지 않는다.

후속 작업은 연결에서 빠진 조건만 요청한다. 같은 파일을 매번 통째로 다시 읽게 하는 대신 버전·증거·유효 범위를 가진 공통 관찰과 필요한 추가 구간을 제공한다. 기존 SourceDelivery는 출처 증거로 유지하고 의미 검증 여부는 별도 필드로 기록한다.

### P1-3: 독립 검토를 반증과 검증 가능한 조건 중심으로 강화하기

Reviewer는 분석 결론을 보기 전 해당 진입점·가드의 기대 동작을 독립적으로 확인하거나, 최소한 결론에 대한 반례를 명시하도록 한다. 입력이 공격자 통제인지, 코드가 실제 등록되는지, 상위 미들웨어/ORM/언어 런타임이 막는지, 영향까지 이어지는지, 제안한 수정이 원인을 독립적으로 없애는지를 확인한다. 모델 두 개의 동의만으로 동적 재현 성공을 표시하지 않는다.

정적 확정과 동적 검증은 별도 상태다. 실행 조건에 의존하는 주장은 pinned lockfile·컨테이너/컴파일러·환경 플래그를 가진 로컬 fixture에서 확인한다. JWT는 실제 설치 라이브러리와 키·알고리즘 설정, Solidity는 실제 컴파일러/배포 바이트코드 조건, 브라우저는 cookie/SameSite/요청 출처를 기록한다. DoS·영구 실패는 격리한 fixture에서 후속 정상 요청까지 확인해야 하며 500 한 번을 영구 실패로 인정하지 않는다.

현재 소스 진단 runtime에는 이 live 검증 엔진이 없다. 기존 reviewer 지시만 강화해 위 실행 검증이 이미 수행되는 것처럼 보고하지 않는다. 검증기를 추가할 때에는 범위·자원·결과 영수증을 가진 별도 계약으로 구현하고 source evidence와 runtime evidence를 구분한다.

### P1-4: 독립 정답셋과 오탐 대조군

현재 7개 파일/행 중심 pilot 정답으로는 전체 성능을 말할 수 없다. 공식 카탈로그의 각 항목을 독립 수정 원인으로 정규화하고, 계정별 정답·보너스 payload·정상 UI·외부 퍼즐은 별도 연결 정보로 둔다. `rootCauseId`는 기존 ground-truth schema에 있으나 평가 분모가 label 수이므로 라벨과 원인 관계 검증, 같은 원인의 중복 label 검출이 필요하다.

각 원인에는 적용 버전, 진입점, 실패 통제, 수정 경계, 근거, 영향, 필요한 실행 조건을 기록한다. 서로 독립적으로 고쳐지는지는 가능한 경우 실제 최소 수정으로 확인한다. 자동 제목/CWE 유사도는 검토 후보 생성에만 쓰고 최종 TP 매칭은 근거로 판정한다.

수정본·안전한 API 사용·fixture 전용 코드·실제 방어가 있는 유사 패턴을 음성 대조군에 포함한다. 현재 BenchmarkCaseSchema는 labels 최소 1개를 요구하므로 순수 음성 case 지원과 Recall 분모 0 처리도 필요하다. 새 원인 정규화 어댑터와 과거 기록 단위 어댑터의 기준을 normalization provenance에 구분하고, 같은 평가에 섞이지 않도록 검사한다. 기존 scoring의 duplicate/inconclusive 처리와 증거 유효율도 함께 점검한다.

새로운 유효 발견은 독립 판정 후 novel-valid로 남기고 다음 버전 정답셋에 편입할 수 있다. 동일 실행의 평가 분모를 결과에 맞춰 늘리거나 줄이지 않는다. 테스트/챌린지 solve 코드가 전체 소스에 포함된 평가와, 이를 제공하지 않은 블라인드 평가의 조건을 구분한다. 알려진 Juice Shop 답안을 일반 분석 프롬프트에 넣어 목표 점수를 맞추지 않는다.

### P2: 도구 보완, 후속 조사, 동적 배치

Semgrep은 현재 규칙이 어떤 위험과 언어를 다루는지부터 기록하고 누락된 서버 입력 검증·인가·비밀값 규칙을 작은 취약/수정 fixture로 검증한다. 단순히 규칙을 늘렸다는 사실보다 **기존 분석이 놓친 고유 정탐 수**와 새 FP를 비교해야 한다. [Semgrep 공식 문서](https://docs.semgrep.dev/writing-rules/glossary)에 따르면 CE는 파일 내 분석에 제한된다. 현재 설치 엔진에 파일 간 추적이 있다고 가정하지 말고 실제 기능·라이선스·언어 지원을 확인해야 한다.

AST의 200개 흐름 상한은 위험도 우선 큐와 나머지 작업의 명시적 후속 처리로 보완한다. source/sink/정제기 모델이 없어 taint가 0인지, 도달 경로가 없어서 0인지, 잘려서 0인지 구분한다. CodeQL 등 추가 도구는 유효한 선택지지만 [GitHub 공식 query suite 설명](https://docs.github.com/en/code-security/concepts/code-scanning/codeql/codeql-query-suites)도 security-extended의 추가 커버리지와 오탐 증가 가능성을 함께 설명한다. 도구 추가만으로 90% 도달을 약속하지 않는다.

이미 동적 배치가 있으므로 고정 16개 슬롯이나 단순 에이전트 증설을 핵심 해결책으로 삼지 않는다. 검토 의무·증거량·언어·미해결 연결 수에 따라 작업을 분할하고, 공통 근거는 재사용한다. 보완 종료는 비용이 아니라 새 근거/조건 해소 여부, 같은 질문 반복, 외부 의존·환경 미지원 같은 명시적 사유로 기록한다. 기존 비용 record-only 정책은 유지한다. 무한 반복 방지와 도구 실행 자원 한도는 금액 제한과 구분한다.

이 표는 개선 우선순위를 위한 사후 분석이며 진단 에이전트에 주입할 정답 목록이 아니다. 한 항목이 다른 그룹과도 관련될 수 있다.

## 6. 단계별 검수와 90% 수용 기준

1. **집계 회귀**: 공유 인용의 서로 다른 원인, 서로 다른 파일의 같은 원인, 동일 원인의 여러 영향, 관찰, 보정 전 주장, 전이 병합/순환, 잘못된 근거·충돌 ID, 전체 Write/patch 우회, 재개 진전, 평가 숫자 변조, 원인 단위 벤치마크 입력을 검사한다. 과거 원본은 보존하고 분류 없음을 null로 표시한다.
2. **작은 통제 실험**: 위 5개 누락 유형·잘못된 병합 사례·언어 버전 반증을 취약/수정 쌍으로 만든다. LLM 전체 실행 전에 도구 규칙·검토 행렬·검증기 계약을 로컬에서 확인한다.
3. **구성요소별 비교**: 동일 모델/소스/도구/환경에서 현행 기준, 집계 변경, 검토 행렬 추가, 경로 연결 추가, 실행 검증 추가를 나누어 비교한다. TP/FP/FN/중복/보류/증거 유효성/비용/시간을 모두 남긴다. 집계 기준 변경으로 건수만 줄어든 효과와 탐지 자체 개선을 구분한다.
4. **고정 정답셋 평가**: 전체 예측을 독립 블라인드 판정한다. 미분류 양성, invalid evidence, 원인 중복이 남으면 90% 완료로 발표하지 않는다. 알려진 정답의 미탐·보류는 Recall에서 놓친 원인으로 남는다.
5. **반복·일반화 평가**: 같은 조건으로 반복한 각 실행에서 Precision/Recall ≥90%를 확인하고 평균·최저값·원인별 재현 빈도를 공개한다. 여러 실행의 좋은 결과를 합친 수치를 단일 실행 점수로 쓰지 않는다. 별도 프로젝트/버전 holdout과 수정본에서 재검증하고 반복 횟수·case 수·신뢰구간을 함께 제시한다. 기존 `evals/offsec/policy.json`의 비교 주장 기준은 적격 case 최소 10개, case별 짝지은 반복 최소 5회이며 한 프로젝트 5회 실행을 10개 case로 셀 수 없다. 이 설정 자체가 90%를 통계적으로 보장하는 것도 아니다. 한 Juice Shop 실행만으로 일반적인 취약점 진단 성능 90%를 주장하지 않는다.

실행할 평가의 비용은 기존 정책대로 기록한다. 이번 변경 검수에는 유료 모델 실행을 사용하지 않았다. 90%는 검증할 목표이며 위 기능 추가별 예상 상승률을 근거 없이 배분하지 않는다.

## 7. 현재 분석 범위와 남은 한계

Scanner는 프로젝트 구조·신뢰 경계·기능 책임을 근거로 파일을 정확히 한 유닛에 배정합니다. 호스트는 범위 누락·중복·범위 밖 파일·교차 흐름 담당을 검사합니다. 설정·스키마·설치/배포 리소스와 의존성 명세도 인벤토리 정책으로 포함합니다. 읽기 실패는 제외한 사실과 사유를 남기고 complete가 되지 않습니다.

작업 기본 용량은 24개 파일·예상 소스 24000토큰입니다. 큰 파일은 UTF-8 바이트 경계를 보존해 나누며, 공통 정의 문맥과 연결 검토가 따로 있습니다. 연결 검토는 선행 범위 분석의 산출물을 받고 실행됩니다. 이 분할은 모든 언어의 함수 의미를 완벽하게 나누는 기능은 아닙니다.

AST는 manifest의 모든 지원 파일을 묶음으로 처리합니다. 500개 기본 잘림은 제거됐으며 미지원 언어·파싱 실패·명시적 제한에 따른 생략은 각각 기록합니다. 호출 그래프·데이터 흐름·taint 경로의 한도는 별도 제한사항입니다. Semgrep은 버전과 규칙 해시가 고정되어 있고 요청·스캔·생략·오류 범위를 기록합니다. AST/검색/도구 결과는 모델에 실제 소스가 전달됐다는 증거를 대신하지 않습니다.

기본 parser는 JavaScript/TypeScript입니다. 다른 언어 parser는 package.json의 선택 peer를 설치합니다. 지원 parser 예시는 Python, Go, Java, Kotlin, C/C++, C#, Rust, PHP, Ruby, Swift, Solidity입니다. parser 설치 여부는 결과에 기록되며 미지원 파일도 직접 소스 분석 대상에 남습니다.

모델 도구 반환의 정확한 행/바이트를 스냅샷과 대조합니다. 긴 줄은 전용 `read_source`의 bounded UTF-8 chunk로 전달할 수 있습니다. 담당 구간 누락, 잘린 줄, 다른 unit의 읽기, Grep만 수행한 결과는 담당 작업의 전달 완료가 아닙니다. 파일별 분석 판정과 실제 인용이 별도로 필요합니다.

Reviewer는 확인한 Finding의 실제 소스 근거를 읽고 채택·수정·기각·불확실을 결정합니다. 부족한 근거는 질문·파일·Finding/flow ID로 요청해 한정 조사합니다. 동일 질문이 반복되거나 보완 한도에 이르면 미해결로 남습니다. 실패한 작업이 제출한 유효 claim도 검토 대기로 보존합니다.

같은 소스 근거에 제목만 다른 Finding은 검토 힌트로 표시합니다. 집계는 Reviewer가 선언한 원인·구성요소·독립 수정 경계를 기준으로 합니다. 원인 분류가 없는 기존 기록에는 독립 수를 추정해 채우지 않습니다. 이 구조 검사는 모델의 의미적 판단이 항상 옳다는 보장이 아니며, 탐지율과 오탐률은 독립 정답 평가가 필요합니다.

원본 무결성과 재사용 호환성은 분리합니다. JS/TS/JSON에서 파싱 가능한 단순 CRLF/LF·마지막 개행 차이만 자동 재사용 대상으로 허용합니다. 문자열/다중 행 literal·BOM·line continuation·미지원 형식은 보수적으로 재분석합니다. 코드 조건·권한 설정·의존 관계가 바뀌면 영향 받는 작업을 다시 분석합니다.

전체 실행 완료는 취약점 부재, 모든 공격 경로 발견, 언어 전체의 의미 동등성, provider 원격 실행의 exactly-once를 뜻하지 않습니다. live pentest/redteam 엔진, HTTP 게이트웨이, 다중 호스트 자동 확장은 이번 소스 진단 runtime의 범위 밖입니다.
